### What READY means

A full local courier run — prepare, review, byte-freeze, validate, MOCK signer handoff, binding
checks, local signature verification — reached `POST_ELIGIBLE=YES` with the byte freeze intact, and
produced a custody seal. Each READY row in the evidence artifact carries its own canonical hash,
payload byte count and seal display.

### What READY does not mean

- not posted, and not authorised to be posted
- not signed by the real canonical signer (`MOCK` mode throughout; `realCanonicalSignerAccessed: false`)
- not economically meaningful, not FLOP eligibility, not counterparty consent

## The one BLOCKED frame

`docs/PHASE3B_ONE_DEAL_PLAN.md` names a `claim` frame as step 2. The adopted pin does not have one:

```
AIRLOCK_REFUSED: tclk: unknown frame type: claim
```

The refusal happens in `prepareFrame`, before an envelope exists — so there is no request id, no
approval, and nothing for the adapter to courier. This is the Airlock refusing to canonicalise a
frame type the pinned protocol does not define, which is the correct behaviour.

At the adopted pin the lifecycle is `offer → accept → lock → reveal → receipt`, with `cancel` and
`refund` as alternates. The claim *step* in the plan is carried by `accept` (the counterparty
publishing the hash-lock statement) followed by `reveal` (the counterparty publishing the preimage).
The plan should be reworded to that vocabulary; no adapter or custody change is implied.

## Custody: unchanged by all six frames

| Property | Value |
| --- | --- |
| TCLK holds key custody | NO |
| Real canonical signer accessed | NO |
| Real signature performed | NO |
| Live Technocore reads | NONE |
| Live Technocore writes | NONE |
| Value moved | NONE |
| Wallet connected | NO |

The adapter passes the canonical signer a room, a text and nothing else, and accepts back
`{ did, room, nonce, signature, text }`. No frame in the Phase 3B plan requires more than that,
which is why readiness could be established without touching custody at all.

One clarification, because it looks like an exception: the `reveal` frame publishes the hash-lock
preimage. That is protocol-intended public data at claim time, not custody material. It is not a
private key, not a seed, and the secret sentinel does not fire on it. The committed happy-path
dry-run artifact still uses an `accept` frame, so no preimage sits in committed evidence.

## Preview cross-check

The two-step committed preview (`accept` in `tclk-offers`, `lock` in a party room) is covered: both
frame types were couriered to READY in this run. The preview's own canonical hashes differ from this
run's because it was built from a different offer instance — the preview pins a specific future
payload, this run demonstrates the frame type is couriered end to end. The preview still declares
`signed: false`, `posted: false`, and its pin matches the adopted pin.

## What must still happen before Phase 3B

1. Reword plan step 2 from `claim` to the `accept` / `reveal` pair.
2. Separately justify and approve a real offline signature; `REAL_INTERFACE_DRY_RUN` is
   `NOT_SUPPORTED` against the current canonical signer, which exposes no non-signing surface.
3. Decide the real destination rooms. The room ids above are derived from a locally constructed
   contract and are not reservations.
4. Obtain counterparty consent for anything posted to a shared venue.
5. Keep public posting disabled until each of the above is closed.
